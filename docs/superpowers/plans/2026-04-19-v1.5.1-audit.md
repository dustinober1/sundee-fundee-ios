# v1.5.1 Audit Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce a consolidated, severity-tagged findings report covering performance, reliability, UX polish, and code health, then triage it into a fix list approved by the user.

**Architecture:** Four parallel `Explore` subagents run independently, each writing a findings file in `docs/superpowers/specs/audit/`. A consolidation step merges them into one report. User approves a triaged fix list; that fix list feeds a second implementation plan.

**Tech Stack:** Agent tool (Explore subagent_type), Markdown, git. No code changes in this plan — it's a discovery plan.

**Companion spec:** `docs/superpowers/specs/2026-04-19-v1.5.1-polish-design.md`

- [ ] **Step 1: Dispatch perf audit agent**

Agent prompt:

> You are auditing the Sundee Fundee iOS app (SwiftUI, Swift 6 strict concurrency, CloudKit) for performance issues. Working dir: `/Users/dustinober/Projects/sundee-fundee`. App code lives in `SundeeFundee/Sources/SundeeFundeeKit/` and `SundeeFundeeApp/`.
>
> Do NOT change any code. Produce a findings report at `docs/superpowers/specs/audit/perf-findings.md`.
>
> Check specifically:
> 1. **Fetch patterns** — Open each major view's view model: `DashboardViewModel`, any Programs VM, `MaxesViewModel`, Workout VMs, `SettingsViewModel`. Look for sequential `await` calls that fetch independent data and could be parallelized with `async let` or `TaskGroup`. Note the file:line and propose the `async let` rewrite.
> 2. **Redundant fetches** — Find views with `.onAppear` or `.task` that trigger `fetchAll` every time the view appears, even when data hasn't changed. Flag candidates for in-memory session caching.
> 3. **Scroll perf** — Find long `List` / `ForEach` views (workout history, benchmarks list, exercise picker). Check for missing `Equatable` on row inputs, heavy body computation per row, unnecessary `@Published` re-renders.
> 4. **Expensive body recomputes** — Look for `@Published` properties that change often and drive broad view re-renders.
> 5. **Asset/image loading** — Share card rendering path, theme assets. Any sync image loads on the main thread?
>
> Output format — markdown with sections per check, each finding in this shape:
> ```
> ### [Finding title]
> **Severity:** high | med | low
> **File:** `relative/path.swift:line`
> **Observation:** [what you saw]
> **Impact:** [why it matters]
> **Proposed fix:** [concrete change]
> ```
>
> Be thorough. This feeds a patch release, so we care about real wins, not speculation. If you can't find issues in an area, say so.

- [ ] **Step 2: Dispatch reliability audit agent**

Agent prompt:

> You are auditing the Sundee Fundee iOS app for reliability issues. Working dir: `/Users/dustinober/Projects/sundee-fundee`. App code lives in `SundeeFundee/Sources/SundeeFundeeKit/` and `SundeeFundeeApp/`.
>
> Do NOT change any code. Produce a findings report at `docs/superpowers/specs/audit/reliability-findings.md`.
>
> Check specifically:
> 1. **SyncQueue** — Read `SundeeFundee/Sources/SundeeFundeeKit/DataLayer/SyncQueue/`. Does the retry/backoff strategy look sound? Are stuck mutations surfaced to the user? What happens to mutations if the app is force-quit mid-flush? Any silent data loss paths?
> 2. **Guest → signed-in migration** — Trace what happens when a guest user signs in with Apple. Is local data (from `LocalDataClient`) migrated to CloudKit? If not, is that intentional or a gap? File: likely `AuthViewModel` and `LocalDataClient`.
> 3. **Decode-resilience logging** — Both `CloudKitClient` and `LocalDataClient` skip records that fail to decode and log warnings. Is that warning signal usable? Would a user ever know? Should persistent decode failures surface somewhere (e.g., Settings diagnostic)?
> 4. **Schema drift** — Compare `SundeeFundeeApp/cloudkit-schema.json` to current Swift models in `DataLayer/Records/` and `Models/`. Any field names/types in models that aren't in schema, or vice versa? Any reserved-name violations (`createdAt`, `modifiedAt`, `startDate`, `endDate`)?
> 5. **Active workout offline edges** — If CloudKit is unreachable mid-workout, does local state survive? Does SyncQueue pick it up?
> 6. **Keychain session restore** — `AuthViewModel.restoreSession()` path. What happens if the user's Apple ID credential is revoked, or the account is deleted Apple-side? Does the app handle gracefully?
>
> Output format — markdown with the same finding shape as the perf audit (see `perf-findings.md`), with severity / file / observation / impact / proposed fix.
>
> Be thorough. If a check turns up clean, say so explicitly.

### Task 4: Triage with user (approval gate)

**Files:**
- Create: `docs/superpowers/specs/2026-04-19-v1.5.1-triage.md`

- [ ] **Step 1: Present triaged fix list to the user**

Build a proposed triage by sorting the consolidated findings into three buckets based on severity + risk + patch-release appropriateness:

- **must-fix** — regressions, bugs, correctness issues, anything user-reported
- **should-fix** — high-impact polish/perf with low regression risk
- **skip** — low impact, high risk, or better deferred to 1.6

Post the bucketed list in chat. Ask the user to approve, adjust, or reject.

- [ ] **Step 2: Apply user's edits**

If the user moves items between buckets, add items, or removes items, update the triage accordingly. Repeat until the user approves.

- [ ] **Step 3: Write triage document**

Format:

```markdown
# v1.5.1 Triage (Approved)

**Date:** 2026-04-19
**Status:** Approved by user
**Source:** `docs/superpowers/specs/2026-04-19-v1.5.1-audit-findings.md`

## must-fix
1. [area] [finding title] — [one-line fix summary] — file:line
2. ...

## should-fix
1. ...

## skip (deferred to 1.6+)
1. ... — [reason]

## Fix ordering (execution)
1. ...
2. ...
```

Ordering heuristic: fix touching the fewest files first, fix with tests second, UI polish last, each area commits as a coherent group.
