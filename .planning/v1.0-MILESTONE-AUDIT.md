## Critical Gaps (Blockers)

### 1. Guest Upgrade Path Dead Code (AUTH-07)

**Root cause:** `sign-in.tsx` auth handlers (`handleAppleSignIn`, `handleGoogleSignIn`, `handleEmailAuth`) create fresh authenticated accounts. None detect the existing anonymous user session or call `guest.upgrade(credential)`. The Phase 9 migration expansion (13 keys, multi-batch, pending flag, retry on launch) is fully implemented and tested but unreachable.

**Impact:** Guest users who create accounts lose all workout history, exercise maxes, readiness surveys, cycle data, and injury profiles. Data remains stranded in AsyncStorage while the repo factory switches to Firestore implementations.

**Fix:** `sign-in.tsx` auth handlers must check if current user is anonymous and call `guest.upgrade(credential)` instead of creating a new account.

### 2. Firestore Security Rules Block Pain Logs (INJR-03, INJR-04)

**Root cause:** `firestore.rules` only covers 1-level subcollections:
```
match /users/{userId} {
  match /{subcollection}/{docId} { allow read, write: if ... }
}
```
Pain logs at `/users/{uid}/injuries/{injuryId}/painLogs/{logId}` are 2 levels deep and fall through to the default deny rule. The Firestore rules test suite has no test for this path.

**Impact:** All `savePainLog()` calls for authenticated users throw a permission-denied error (silently caught by try/catch). Pain trend analysis always receives empty data. Guest users are unaffected (AsyncStorage path works).

**Fix:** Add a 2-level subcollection match or recursive wildcard:
```
match /{sub1}/{doc1}/{sub2}/{doc2} {
  allow read, write: if request.auth != null && request.auth.uid == userId;
}
```

### 3. Weight Unit Not Threaded Everywhere (PLAT-05 partial)

**Files:** `HistoryCard.tsx` (lines 56-58), `exercise-detail.tsx` (lines 139, 151, 171)

Both hardcode "lbs" for weight/volume display. The fix pattern exists in `workout-detail.tsx` (Phase 10): load `weightUnit` from `SettingsRepo` in a `useEffect`, pass to `formatWeight`. These 2 screens need the same treatment.
