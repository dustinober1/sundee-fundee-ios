    - step-cycle: toggle/switch for cycle opt-in, this is the final step, Next triggers save
    - All screens show progress bar at top (step N of 5, or N of 4 for male users)
    - All screens show Back button except step-name (first step)

  <action>
    **Step 1: Create OnboardingContext.tsx**
    - Define `OnboardingDraft` interface: `{ name: string; experienceLevel: ExperienceLevel | null; primaryGoal: PrimaryGoal | null; gender: Gender | null; cycleOptIn: boolean }`
    - Create React context with draft state + setter functions + `completeOnboarding(uid: string, isGuest: boolean): Promise<void>`
    - `completeOnboarding` calls `getOnboardingProfileRepo(isGuest).saveProfile(uid, { ...draft, hasCompletedOnboarding: true })` — atomic save per locked decision
    - NO partial saves during the flow — all data saved at once on completion
    - Wrap in `OnboardingProvider` component

    **Step 2: Create useOnboardingFlow.ts**
    - Export `ONBOARDING_STEPS` array: `['step-name', 'step-experience', 'step-goal', 'step-gender', 'step-cycle']`
    - Export `getStepIndex(stepName: string): number`
    - Export `getNextStep(currentStep: string, draft: OnboardingDraft): string | null`
      - If currentStep is 'step-gender' and draft.gender is 'male': return null (signals completion)
      - If currentStep is 'step-cycle': return null (final step, signals completion)
      - Otherwise: return next step in STEPS array
    - Export `getTotalSteps(gender: Gender | null): number` — returns 4 for 'male', 5 for others
    - Export `getPreviousStep(currentStep: string): string | null` — returns null for step-name

    **Step 3: Create onboarding test files**
    - `OnboardingContext.test.tsx`: Test that completeOnboarding calls saveProfile with all draft fields + hasCompletedOnboarding: true. Test that draft starts with empty/null values.
    - `useOnboardingFlow.test.ts`: Test getNextStep skips cycle for male. Test getNextStep returns 'step-cycle' for female. Test getNextStep returns null for step-cycle (last step). Test getTotalSteps returns 4 for male, 5 for female/other. Test getPreviousStep returns null for step-name.

    **Step 4: Create onboarding route layout**
    - `app/(onboarding)/_layout.tsx`: Wrap children in `OnboardingProvider`. Use a `Stack` navigator with `headerShown: false`. This creates the (onboarding) route group.

    **Step 5: Create 5 step screens**
    Each screen follows the same pattern:
    - Use Art Deco styling (CREAM background, NAVY text, ORANGE accent/buttons)
    - Show progress bar at top: current step / total steps (use getTotalSteps)
    - Show Back button (except step-name which is first)
    - Show Next/Complete button at bottom, disabled until selection made
    - Use `useOnboardingFlow` to determine navigation target on Next press
    - On the final step (step-cycle for non-male, step-gender for male): Next button calls `completeOnboarding(uid, isGuest)` then navigates to '/(app)/(tabs)'

    Screen details:
    - `step-name.tsx`: TextInput for name, placeholder "What should we call you?", keyboard-aware
    - `step-experience.tsx`: 3 cards — Beginner ("New to strength training"), Intermediate ("1-3 years"), Advanced ("3+ years")
    - `step-goal.tsx`: 5 cards — Strength, Build Muscle, Endurance, Weight Loss, General Fitness
    - `step-gender.tsx`: 3 cards — Female, Male, Prefer Not to Say (maps to 'other' Gender type). If Male selected and Next pressed, skip cycle step and call completeOnboarding directly.
    - `step-cycle.tsx`: Descriptive text about cycle tracking benefits + toggle switch. Default cycleOptIn = false. Only shown for female/other gender.

    **IMPORTANT per locked decisions:**
    - One question per screen with progress bar
    - Back button on each step to revisit/change answers
    - All data saved at once on final step (no partial persistence)
    - Guests go through same flow as authenticated users
    - After completion, land on Dashboard tab

    **Update app/_layout.tsx (root layout):**

    The root layout must gate between onboarding and the main app based on the `hasCompletedOnboarding` flag from the user profile.

    1. Add state: `const [onboardingComplete, setOnboardingComplete] = useState<boolean | null>(null)` — null = loading/unknown, false = needs onboarding, true = skip to app.

    2. In the existing `handleUserSignIn` callback (which fires on auth state change), after persisting the user profile, also check `hasCompletedOnboarding`:
       - For authenticated users: `const profile = await new FirestoreUserRepo().getUser(user.uid)` — read profile to check `hasCompletedOnboarding`
       - For guests: `const profile = await new LocalUserRepo().getUser(user.uid)` — same check
       - Set `onboardingComplete` based on `profile?.hasCompletedOnboarding ?? false`

    3. When `onboardingComplete` is null (still loading), return a loading/splash view (plain View with CREAM background — no flicker)

    4. Add the `(onboarding)` route to the Stack:
       ```tsx
       <Stack>
         <Stack.Screen name="sign-in" options={{ headerShown: false }} />
         <Stack.Screen name="verify-email" options={{ headerShown: false }} />
         <Stack.Screen name="(onboarding)" options={{ headerShown: false }} />
         <Stack.Screen name="(app)" options={{ headerShown: false }} />
       </Stack>
       ```

    5. **CRITICAL (from research pitfall 3):** Do NOT evaluate routing until profile is loaded. The `null` loading state prevents the "onboarding flicker" where users see onboarding briefly before being redirected to the app.

    **Update app/(app)/_layout.tsx:**

    Add the onboarding completion check. The existing Redirect guard for auth should also check `hasCompletedOnboarding`. If authenticated but NOT onboarded, redirect to `/(onboarding)/step-name`.

    **Routing flow:**
    - Not signed in -> sign-in screen (existing)
    - Signed in, not onboarded -> /(onboarding)/step-name
    - Signed in, onboarded -> /(app)/(tabs) (existing)

    **IMPORTANT:**
    - Use the Redirect component pattern already established in app/(app)/_layout.tsx — this project uses `<Redirect href="...">` for route guards, not Stack.Protected (the research mentions Stack.Protected but the codebase already uses the Redirect pattern from Phase 1 decision [01-03])
    - If Stack.Protected is available and works, it can be used, but the Redirect pattern is proven in this codebase and is acceptable
    - Show loading state (null return or splash) until profile is loaded — NEVER default to `false` for hasCompletedOnboarding as this causes flicker
