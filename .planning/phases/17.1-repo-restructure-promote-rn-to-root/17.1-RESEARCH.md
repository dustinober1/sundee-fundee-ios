# Phase 17.1: Repo Restructure: Promote RN to Root - Research

**Researched:** 2026-03-17
**Domain:** Git repository restructuring, Expo/React Native project layout, Firebase tooling path references
**Confidence:** HIGH

## Summary

The React Native + Expo app currently lives at `SundeeFundeeRN/` (a subdirectory of the repo root). The legacy Swift/SwiftUI app occupies the root alongside Xcode project files, the WOD admin Next.js dashboard at `wod-dashboard/`, and Firebase tooling files. The goal of Phase 17.1 is to promote the RN app to the repo root so that `cd SundeeFundeeRN && ...` becomes just `...` from the repo root. This is a pure restructuring operation — no code logic changes.

The key complexity is that the repo root already contains conflicting artifacts from the legacy Swift era (`.xcodeproj`, `SundeeFundee/`, `SundeeFundeTests/`, `project.yml`, `Gemfile`, `fastlane/`, `ci_scripts/`). The plan must decide whether to delete, archive, or move legacy Swift artifacts. Additionally, Firebase tooling (`firebase.json`, `.firebaserc`) references `SundeeFundeeRN/firestore.rules`, and the root `package.json` has a ghost dependency entry that needs to be merged. The iOS native `/ios` and Android `/android` directories are generated by Expo and listed in `SundeeFundeeRN/.gitignore` as ignored — they will exist on disk but are not committed.

**Primary recommendation:** Move all `SundeeFundeeRN/` contents to the repo root, archive or delete legacy Swift artifacts (they are explicitly noted as no longer under active development), update `firebase.json` rules path, update `CLAUDE.md`, and update the root-level `app.json` to be the merged EAS + full Expo config.

### Pattern 1: git mv for tracked files
**What:** Use `git mv` instead of shell `mv` to move tracked files while preserving git history and enabling `git log --follow`.
**When to use:** For every tracked source file being promoted.

```bash
# Move tracked files/dirs from subdirectory to root
git mv SundeeFundeeRN/app ./app
git mv SundeeFundeeRN/src ./src
git mv SundeeFundeeRN/__mocks__ ./__mocks__
git mv SundeeFundeeRN/assets ./assets
# ... etc for each tracked item
```

### Pattern 2: App.json merge strategy
**What:** The repo currently has TWO `app.json` files:
- Root `app.json`: minimal stub containing only `expo.extra.eas.projectId`
- `SundeeFundeeRN/app.json`: full Expo config

The root stub was likely created by an early EAS init. After the move, `SundeeFundeeRN/app.json` becomes the canonical `app.json` at root — no merge needed; just promote it and delete the root stub.

### Pattern 3: package.json merge
**What:** Root `package.json` contains `react-native-purchases` and `react-native-purchases-ui` as dependencies — these are already in `SundeeFundeeRN/package.json`. After the move, root `package.json` is replaced by the promoted one. Verify `react-native-purchases` is already present in the RN `package.json` (confirmed: `"react-native-purchases": "^9.12.0"` exists).

### Pattern 4: Legacy Swift archival
**What:** The CLAUDE.md explicitly labels the Swift codebase as "Legacy iOS App (Reference Only)" and "no longer under active development." Two options:

| Option | Approach | Tradeoff |
|--------|----------|----------|
| A | Move Swift artifacts to `_legacy-swift/` subfolder | Preserves history, clean root, git mv tracks the move |
| B | Delete Swift artifacts entirely | Cleaner, loses local reference, history still in git |
| C | Leave Swift artifacts at root | Cluttered root, confusing for EAS/Expo tooling |

**Recommendation:** Option A — move to `_legacy-swift/`. The CLAUDE.md says "kept for reference" so deletion is unilateral. A `_legacy-swift/` folder with a README noting it's archived is safe.

### Anti-Patterns to Avoid
- **Shell `mv` for tracked files:** Loses git history — always use `git mv` for tracked items or commit the move so git detects the rename by content similarity (>50%).
- **Running `npm install` before committing the move:** The `node_modules` from `SundeeFundeeRN/` is gitignored; installing at the new root creates a fresh `node_modules` in the right place, which is correct — but do it after committing the file moves.
- **Forgetting `firebase.json`:** The `"rules": "SundeeFundeeRN/firestore.rules"` path will break Firebase CLI deploy after the move. Must be updated to `"rules": "firestore.rules"`.
- **Conflicting root `app.json`:** The root stub `app.json` must be replaced, not appended-to. Git will see this as a modification to an existing tracked file.
- **EAS project ID mismatch:** `app.json` must retain `"extra.eas.projectId": "dc7c3b9d-ee13-4713-8fab-85389863e18f"`. Confirmed present in `SundeeFundeeRN/app.json`.
- **Broken moduleNameMapper in jest.config.js:** The `@/*` → `./*` alias is relative to `rootDir`. After promotion, `rootDir` becomes the repo root and the same alias resolves correctly as long as `jest.config.js` is at root.

## Common Pitfalls

### Pitfall 1: Two `app.json` files in git conflict
**What goes wrong:** Promoting `SundeeFundeeRN/app.json` to root while the root `app.json` stub exists results in a staged deletion + modification, not a clean rename.
**Why it happens:** Git tracks the root `app.json` as an existing file; `git mv SundeeFundeeRN/app.json ./app.json` will fail because `./app.json` already exists.
**How to avoid:** Delete the root stub `app.json` first (`git rm app.json`), then `git mv SundeeFundeeRN/app.json ./app.json`.
**Warning signs:** `git status` shows both modified `app.json` and renamed `SundeeFundeeRN/app.json`.

### Pitfall 2: Two `package.json` files — same trap
**What goes wrong:** Root `package.json` is a tracked file. `git mv SundeeFundeeRN/package.json ./package.json` will fail.
**How to avoid:** `git rm package.json` first, then promote the RN one. Verify the promoted `package.json` already contains all deps (RevenueCat entries from root stub are already in the RN `package.json`).

### Pitfall 3: `google-services.json` is gitignored in root `.gitignore` but untracked in RN dir
**What goes wrong:** `google-services.json` shows as `??` (untracked) in the current `git status`. After the move it needs to be at root as `./google-services.json`. Since it's not tracked, `git mv` won't work — use `mv` (shell) instead. Similarly `GoogleService-Info.plist` is gitignored and must be manually copied.
**How to avoid:** Handle secrets (untracked/gitignored files) separately with plain `mv` after all `git mv` operations are staged. Confirm `google-services.json` is in root `.gitignore` (currently it only ignores `GoogleService-Info.plist` for iOS — `google-services.json` is NOT in the root `.gitignore`, so it will be untracked/visible after the move).

### Pitfall 4: `firebase.json` rules path breaks silently
**What goes wrong:** Firebase CLI will fail on `firebase deploy --only firestore:rules` with a file-not-found error if `SundeeFundeeRN/firestore.rules` path is still in `firebase.json`.
**How to avoid:** Update `firebase.json` `"rules"` key to `"firestore.rules"` as part of the same commit.

### Pitfall 5: `ios/` and `android/` are gitignored in `SundeeFundeeRN/.gitignore`
**What goes wrong:** After promotion, the root `.gitignore` does NOT have `/ios` and `/android` as ignored entries. The generated native directories will appear as untracked.
**How to avoid:** Merge `SundeeFundeeRN/.gitignore` into root `.gitignore` — specifically add `/ios`, `/android`, `.expo/`, `dist/`, `web-build/`, and other RN-specific ignores from the RN gitignore.

### Pitfall 6: `node_modules` at two levels
**What goes wrong:** `SundeeFundeeRN/node_modules/` is gitignored. After promotion, there is no `node_modules/` at root (or the old Swift-era one may linger). Running Expo from root will fail until `npm install` is run at root.
**How to avoid:** After committing the file moves, run `npm install` from the repo root. Confirm the root `.gitignore` includes `node_modules`.

### Pitfall 7: CLAUDE.md command references break
**What goes wrong:** CLAUDE.md contains 10+ references to `cd SundeeFundeeRN && ...`. These will be misleading after the restructure.
**How to avoid:** Update CLAUDE.md commands to remove the `cd SundeeFundeeRN &&` prefix.

### Pitfall 8: `.planning/` relative paths in GSD tooling
**What goes wrong:** GSD tooling (`.claude/`) uses relative paths from the repo root. These remain unchanged since `.planning/` stays at root. Not a risk — just worth confirming.
