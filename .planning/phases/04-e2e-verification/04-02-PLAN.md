  <files>tests/e2e/pr-celebration.spec.ts</files>
  <action>
    Create `tests/e2e/pr-celebration.spec.ts` implementing TEST-02: verifying that the PR celebration overlay triggers when a user lifts more than their previous best.

    **Critical context — PR detection guard**: `checkWeightPR` in `use-pr-detection.ts` returns `true` only when `newWeight > currentMax && currentMax > 0`. This means the user MUST have a prior 1RM record in IndexedDB before the test workout, otherwise the first lift will never trigger a PR (by design — "no PR on first session" decision).

    **Test flow:**

    1. Navigate to `/onboarding`, call `completeOnboarding(page, 'PR Test User')`
    2. **Read the user ID from IndexedDB** — needed to seed the 1RM record with the correct userId:
       ```typescript
       const userId = await page.evaluate(async () => {
         return new Promise<string>((resolve, reject) => {
           const request = indexedDB.open('StrengthApp', 4);
           request.onsuccess = (event) => {
             const db = (event.target as IDBOpenDBRequest).result;
             const tx = db.transaction('users', 'readonly');
             const store = tx.objectStore('users');
             const getAll = store.getAll();
             getAll.onsuccess = () => {
               const users = getAll.result;
               if (users.length > 0) resolve(users[0].id);
               else reject(new Error('No user found'));
             };
             getAll.onerror = () => reject(getAll.error);
           };
           request.onerror = () => reject(request.error);
         });
       });
       ```
    3. **Seed a prior 1RM record for `pause-squat`** (the first exercise in Support Session A):
       ```typescript
       await page.evaluate(({ userId }) => {
         return new Promise<void>((resolve, reject) => {
           const request = indexedDB.open('StrengthApp', 4);
           request.onsuccess = (event) => {
             const db = (event.target as IDBOpenDBRequest).result;
             const tx = db.transaction('oneRepMaxes', 'readwrite');
             const store = tx.objectStore('oneRepMaxes');
             store.put({
               id: 'seed-1rm-pause-squat',
               userId,
               exerciseId: 'pause-squat',
               weight: 100,
               date: new Date().toISOString(),
             });
             tx.oncomplete = () => resolve();
             tx.onerror = () => reject(tx.error);
           };
           request.onerror = () => reject(request.error);
         });
       }, { userId });
       ```
       Using `pause-squat` exercise with a prior 1RM of 100 lbs. The test will enter a weight > 100 to trigger the PR.
    4. **Navigate to workout page and start session**:
       - Go to `/workout/back-squat-complete-cycle`
       - Click "Support Session A"
       - Wait for exercises to render
    5. **Enter a weight higher than the seeded 1RM (100)**:
       - Find the first weight input (`input#weight-1` or first `input[type="number"]`)
       - Fill with `'135'` — this exceeds the seeded max of 100
       - The `onSetChange` handler fires, `checkWeightPR('pause-squat', 135)` evaluates: `135 > 100 && 100 > 0` → `true`
       - PRCelebration component renders with `isVisible: true`
    6. **Assert the PR celebration overlay appears**:
       - The PRCelebration component renders a `<motion.div>` with class `fixed inset-0 z-[200]` containing "New PR!" text
       - Assert: `await expect(page.getByText('New PR!')).toBeVisible({ timeout: 5000 });`
       - Also assert the PR type subtitle: `await expect(page.getByText('New Weight Record!')).toBeVisible();`
       - For confetti detection (optional, may be flaky): `canvas-confetti` creates a `<canvas>` element in the DOM. Can check with `await expect(page.locator('canvas')).toBeVisible({ timeout: 3000 });` BUT this may be unreliable due to timing. The "New PR!" text assertion is the primary signal.
    7. **Dismiss the celebration**: Click the overlay (it has `onClick={onDismiss}`) or wait 3.5 seconds for auto-dismiss.

    **Important notes:**
    - The `useUser()` context provides `oneRepMaxes` which is loaded from Dexie on mount. We seed the 1RM BEFORE navigating to the workout page so the context loads it.
    - **MANDATORY**: After seeding the 1RM in IndexedDB, call `await page.reload()` then `await page.waitForURL('**/dashboard')` to force UserContext to re-mount and re-read `oneRepMaxes` from Dexie. Without this reload, the in-memory context from onboarding won't include the seeded 1RM, and `checkWeightPR` will see `currentMax === 0` — never triggering a PR.
    - The seeded 1RM also provides the prescribedWeight calculation: `Math.round(100 * 0.60) = 60 lbs` for pause-squat. The recommendation engine will suggest a weight based on this.
    - If the weight input is pre-filled with a recommendation ≤ 100, manually clearing and entering 135 should still trigger the PR.

    **Resilient assertion pattern:**
    ```typescript
    // Primary: text assertion on the PR overlay
    await expect(page.getByText('New PR!')).toBeVisible({ timeout: 5000 });
    // Secondary: the subtitle confirms weight type
    await expect(page.getByText('New Weight Record!')).toBeVisible();
    ```

  <files>tests/e2e/sync-verification.spec.ts</files>
  <action>
    Create `tests/e2e/sync-verification.spec.ts` implementing TEST-03: verifying that the sync wiring is active by confirming the workout ID is enqueued in the localStorage sync queue after workout completion.

    **Background**: The `playwright.config.ts` (updated in 04-01) sets `NEXT_PUBLIC_SUPABASE_URL=http://localhost:54321` and `NEXT_PUBLIC_SUPABASE_ANON_KEY=fake-anon-key-for-testing` in the webServer env block. This makes `createClient()` return a non-null Supabase client, which means `isSyncConfigured` is `true` in the sync engine.

    **Sync flow**: After `handleWorkoutComplete` runs:
    1. Workout is saved to IndexedDB (Dexie)
    2. `syncAfterWorkout(workoutId)` is called
    3. Since `isSyncConfigured` is true but user is NOT authenticated (no real auth server), the sync engine enqueues the workout ID to the localStorage sync queue (`sync_pending_workout_ids`)

    This test proves the sync infrastructure is correctly wired: the Supabase client is initialized (env vars work), `syncAfterWorkout` is called after completion, and the queue mechanism functions. The actual remote delivery is a concern for integration tests with a real Supabase instance.

    **Test flow:**

    ```typescript
    import { test, expect } from '@playwright/test';
    import { completeOnboarding } from './helpers/onboarding';

    test.describe('Sync Verification (TEST-03)', () => {
      test('enqueues workout for sync after completion', async ({ page }) => {
        // 1. Complete onboarding
        await page.goto('/onboarding');
        await completeOnboarding(page, 'Sync Test User');

        // 2. Navigate to workout, select session, fill sets, complete workout
        // (same flow as workout-flow.spec.ts)
        await page.goto('/workout/back-squat-complete-cycle');
        await page.getByText('Support Session A').click();
        // Wait for exercise card to render
        await page.waitForSelector('input[type="number"]');
        // Fill first weight input
        await page.fill('input#weight-1', '135');
        // Click Complete Workout
        await page.getByRole('button', { name: 'Complete Workout' }).click();

        // 3. Wait for async operations (IndexedDB write + sync attempt)
        await page.waitForTimeout(1000);

        // 4. Check localStorage sync queue
        const queue = await page.evaluate(() => {
          const raw = localStorage.getItem('sync_pending_workout_ids');
          return raw ? JSON.parse(raw) : [];
        });

        // Workout ID should be in the queue (queued because user is not authenticated)
        expect(queue.length).toBeGreaterThan(0);
      });
    });
    ```

    **Key details:**
    - The localStorage key is `sync_pending_workout_ids` — this is set by the sync queue module when sync is configured but auth is not available
    - Do NOT set up `page.route()` interceptors or mock auth — this test intentionally runs in the unauthenticated state to verify queue behavior
    - The test is deterministic: no auth = always queues, no flakiness from mock timing
    - Import `completeOnboarding` from `'./helpers/onboarding'`
